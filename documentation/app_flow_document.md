# App Flow Document for llm-comparator

## Onboarding and Sign-In/Sign-Up
A brand-new user arrives at the landing page of the llm-comparator application simply by entering its URL in a browser. There is no requirement to create an account or sign in, so the user is immediately presented with the comparison interface. The landing page header displays the application name and a brief invitation to try out the model comparison tool. Since there is no sign-in or sign-up feature, there are no password recovery flows or social login options. The entire experience is public and instantly accessible without any form of authentication.

## Main Dashboard or Home Page
After the landing page finishes loading, the user sees the main dashboard, which centers on a prompt input area at the top. The header contains the application title on the left and a small information icon on the right that opens an about dialog explaining usage. Beneath the header, the prompt input field spans the width of the page, inviting users to type or paste a query or scenario. Below the input field, a set of checkboxes or toggles lists the available LLM providers by name, allowing the user to select one or more models to compare. At the bottom of this section, a single primary button labeled “Compare” triggers the comparison process. The rest of the page is reserved for displaying responses side by side once the comparison completes.

## Detailed Feature Flows and Page Transitions
When the user enters a prompt and clicks the Compare button, the interface captures the input text and the list of selected models. The button transforms into a loading spinner and sends a POST request to the unified chat API endpoint at `/api/chat`. The backend receives the prompt and iterates through each configured provider adapter. For each adapter, it makes an external API call to the corresponding LLM service, attaches any provider-specific parameters, and awaits the response. Errors and rate-limit responses are caught and formatted by the backend before continuing to the next provider. Once all responses or error messages return, the backend compiles them into a JSON array and replies to the frontend.

Upon receiving the consolidated results, the frontend replaces the loading spinner with a grid layout. Each column in the grid corresponds to one LLM provider and displays the provider name as a header. Under each header, the text response appears in a scrollable container that adjusts height to match the tallest column. If any provider returned an error or timed out, its column shows a styled error message explaining the failure. The user can scroll through the results vertically and horizontally if there are many models. At the bottom of the result section, a secondary button labeled “New Comparison” clears the inputs and results, smoothly scrolling the page back to the top.

If the user changes their mind about which models to compare, they can adjust the toggles above the prompt field and press the Compare button again. The page does not perform a full reload; instead, it reuses the same API endpoint and updates only the result grid. The URL in the browser’s address bar remains constant because the application relies on client-side routing within the single page.

## Settings and Account Management
There are no settings or account management pages exposed to end users. All provider configurations, such as API keys and model names, are handled in environment variables and code-level adapters. Developers update a `.env` file with the necessary credentials for each LLM provider and restart the application for changes to take effect. The project includes a `.devcontainer` setup for standardizing development environments, but this is strictly for developer onboarding and not visible in the user interface.

## Error States and Alternate Paths
If the user clicks Compare without entering any prompt text, the application displays an inline validation message below the input field that reads “Please enter a prompt to compare.” No API call is made in this case. If the network connection drops while waiting for responses, a full-width banner appears at the top of the page stating “Network error. Please check your connection and try again.” The Compare button reverts to its original state, allowing the user to retry. When a provider’s API key is missing or invalid, its column shows a specific error message such as “Invalid credentials for OpenAI.” The other providers continue to display their results if available. When the server returns unexpected data or reaches a rate limit, the backend ensures an error object with a human-friendly message is sent so the frontend can display it in context without breaking the layout.

## Conclusion and Overall App Journey
From the moment a user arrives at the landing page to the display of side-by-side LLM responses, the journey remains straightforward and focused. There is no account creation or login, so users dive straight into entering prompts and selecting models. Behind the scenes, the unified API coordinates with multiple external LLM services and handles errors gracefully. The result grid offers an immediate comparison view, and users can quickly start new comparisons without page reloads. Through simple interactions and clear feedback, llm-comparator streamlines the process of evaluating multiple language models in parallel.
